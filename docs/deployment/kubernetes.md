# Kubernetes (ECK + kustomize)

`deploy/kubernetes` runs the same profiles as Docker Compose on Kubernetes, with Elasticsearch,
Kibana and Logstash managed by the [ECK operator](https://www.elastic.co/guide/en/cloud-on-k8s/current/index.html).

```
deploy/kubernetes/
├── base/                    siem: Elasticsearch, Kibana, Logstash (all source pipelines), bootstrap Job
├── components/
│   ├── platform/            AI triage pipeline: NATS + 8 services
│   └── production/          3 ES nodes with anti-affinity + PDB, 2 Kibana, 2 replicas of stateless services
└── overlays/
    ├── lab/                 base + platform, 1 ES node, local images (kind, k3d, Docker Desktop, minikube)
    ├── onprem/              base + platform + production, images from GHCR, LoadBalancer for Logstash
    └── gke/                 onprem + standard-rwo disks, 14-day hot tier, GCS snapshots, Workload Identity
```

The manifests read files from `integrations/sources` and `content`, so kustomize needs
`--load-restrictor LoadRestrictionsNone`. Plain `kubectl apply -k` does not accept that flag; pipe
`kubectl kustomize` into `kubectl apply` instead.

## 1. Install the ECK operator (once per cluster)

```bash
kubectl create -f https://download.elastic.co/downloads/eck/3.5.0/crds.yaml
kubectl apply  -f https://download.elastic.co/downloads/eck/3.5.0/operator.yaml
```

## 2. Create the secrets file

```bash
./deploy/kubernetes/init-secrets.sh lab          # Windows: .\deploy\kubernetes\init-secrets.ps1 lab
```

This writes `deploy/kubernetes/overlays/<overlay>/secrets.env` (git-ignored) with the passwords
of `logstash_ingest` and `esm_platform`, the MCP token, and an empty `LLM_API_KEY`. The `elastic`
password is generated by ECK (`kubectl -n esm get secret esm-es-elastic-user -o jsonpath='{.data.elastic}' | base64 -d`).

## 3. Apply an overlay

```bash
kubectl kustomize --load-restrictor LoadRestrictionsNone deploy/kubernetes/overlays/lab \
  | kubectl apply --server-side --force-conflicts -f -
kubectl -n esm get elasticsearch,kibana,logstash,pods
```

The `esm-bootstrap` Job waits for Elasticsearch and Kibana, then loads ILM, templates, roles, users
and the detection rules. Jobs cannot be changed in place: before re-applying changed content run
`kubectl -n esm delete job esm-bootstrap --ignore-not-found`.

Generated ConfigMaps and Secrets keep fixed names (ECK resources do not follow kustomize's hashed
names), so restart workloads after changing them, e.g. `kubectl -n esm rollout restart deployment`.

## 4. Reach the services

| What | Service | Lab access |
| --- | --- | --- |
| Kibana | `esm-kb-http:5601` | `kubectl -n esm port-forward svc/esm-kb-http 5601` |
| Log inputs | `esm-ls-ingest` (ports in [integrations/sources](../../integrations/sources/README.md)) | `kubectl -n esm port-forward svc/esm-ls-ingest 5514:5514` (TCP only) |
| Cases API | `bff:8080` | `kubectl -n esm port-forward svc/bff 8080` |
| MCP server | `mcp-server:8090` | `kubectl -n esm port-forward svc/mcp-server 8090` |

In `onprem` and `gke` the Logstash Service is a `LoadBalancer`; point firewalls and Beats at its
external address. Expose Kibana through your ingress controller with TLS.

## Overlay notes

**lab** uses images `esm/<service>:dev`. Build them with
`docker compose -f deploy/compose/siem.yml -f deploy/compose/platform.yml build` and load them into
the cluster. With kind on Docker Desktop (containerd image store), `kind load docker-image` fails with
`content digest ... not found` for multi-platform images; save a single platform instead:

```bash
for img in esm/bff:dev docker.elastic.co/elasticsearch/elasticsearch:8.13.4; do   # ...every image
  docker save --platform linux/amd64 -o img.tar "$img" && kind load image-archive --name esm img.tar
done
```

**onprem** pulls `ghcr.io/yusufarbc/elastic-genai-secops/<service>:latest` (published by CI from
`production`). Set your StorageClass with the commented patch in `overlays/onprem/kustomization.yaml`.
For snapshots to S3-compatible storage, enable `components/snapshots-s3` there
([snapshots](../components/elasticsearch.md#snapshots)).

**gke** before applying:

1. Replace `PROJECT_ID` in `overlays/gke/serviceaccounts.yaml` and `overlays/gke/kustomization.yaml`,
   and `GCS_BUCKET` in `overlays/gke/kustomization.yaml`.
2. Create the GCP service accounts and bind them:

   ```bash
   gcloud iam service-accounts create esm-snapshots
   gcloud storage buckets add-iam-policy-binding gs://GCS_BUCKET \
     --member serviceAccount:esm-snapshots@PROJECT_ID.iam.gserviceaccount.com --role roles/storage.objectAdmin
   gcloud iam service-accounts add-iam-policy-binding esm-snapshots@PROJECT_ID.iam.gserviceaccount.com \
     --role roles/iam.workloadIdentityUser --member "serviceAccount:PROJECT_ID.svc.id.goog[esm/esm-elasticsearch]"
   # only with LLM_PROVIDER=vertex: same for esm-platform with roles/aiplatform.user
   ```

3. The `esm-gcs-snapshots` Job registers repository `esm-gcs` and the daily policy `esm-daily`
   (`SNAPSHOT_EXPIRE_AFTER`, default 730 days, is the regulatory retention; the hot tier keeps 14 days).
   The overlay sets `SNAPSHOT_POLICY=esm-daily`, so ILM deletes an index from the hot tier only
   after `esm-daily` has snapshotted it; the bootstrap Job waits for this Job to create the policy.

## LLM provider

Edit `LLM_PROVIDER`, `LLM_MODEL_ID` and `LLM_BASE_URL` in the `esm-platform-config` literals
(`components/platform/kustomization.yaml`, or a patch in your overlay) and put the API key in
`secrets.env` as `LLM_API_KEY`. See [triage-pipeline.md](../genai/triage-pipeline.md#choosing-the-llm).

## Limits

- `detection-service` must run with one replica (it owns the alert checkpoint). `alert-gateway` can
  scale out: its correlation windows are in the NATS bucket `esm-correlation` (ADR-027).
- No NetworkPolicies yet; restrict access to `masking-service` before production.
- No Fleet / Elastic Agent resources yet (planned).
